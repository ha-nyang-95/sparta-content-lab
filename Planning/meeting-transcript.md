- 원본 영상: https://www.youtube.com/watch?v=IF8NcoyZXd0
- 채널: 그냥저냥 / 업로드: 2026-07-15 / 길이: 약 24분
- 자막 종류: 한국어 자동 생성(ASR). 띄어쓰기·인식 오류가 많아 **의미가 분명한 부분만 재구성**했고, 불확실한 대목은 `(불명확)`으로 표시했다.
- 화자: **운영자** = 일본인 대상 한국어 교육 채널 운영자(발주자) / **개발자** = 구현 담당

## 2. 운영자가 설명한 현재 상황

### 하는 일
일본인을 대상으로 **일본어로 한국어를 가르치는** 콘텐츠를 만든다. 채널 구독자는 약 1만 명대이고 계속 키우고 싶어 한다.

### 지금의 조사 방식
주 1회 정도 직접 시장조사를 한다. 보는 것은 세 가지다.

1. 최근 잘 나가는 트렌딩 주제
2. **에버그린 콘텐츠** — 일본 사람들이 한국어가 궁금할 때 검색해서 한 번씩 찾아보는, 검색 유입으로 꾸준히 도는 콘텐츠
3. 주변 경쟁 채널에서 잘 나간 영상들

### 왜 힘든가
- 일본어로 한국어를 가르치는 채널만 봐서는 **표본이 너무 적다**. "한국에서 베트남어 배우는 채널"을 찾는 것과 비슷한 수준으로 소스 자체가 희소하다.
- 그래서 실제로는 영어로 한국어를 가르치는 채널, 한국에서 일본어를 가르치는 채널, 유명한 한국어 교육 채널까지 전부 참조한다.
- 이 과정에 **시간이 너무 많이 걸린다**.

---

## 3. "좋은 영상"의 정의 (운영자의 기준)

운영자가 이미 나름의 정의를 갖고 있고, 두 축으로 나뉜다.

**① 구독자 수 대비 조회수가 높은 영상**
> "구독자가 적은데 갑자기 조회수가 확 나오는 것 — 그건 그 사람의 인기보다 **콘텐츠의 가치**가 크기 때문이다. 그런 영상을 찾아내는 게 중요하다."

**② 시간이 지나도 조회수가 꾸준히 오르는 영상**
> 알고리즘을 타서 순간적으로 터진 것 말고, **검색으로 꾸준히 유입되는** 영상. 이게 에버그린이다.

이 두 종류를 구분해서 볼 수 있어야 한다.

---

## 4. 조사 범위 — 어디까지 넓히나

개발자가 "왜 동종 채널만 보면 안 되느냐"고 물었고, 운영자의 답은 다음과 같다.

- **언어 교육은 카테고리 공통점이 있다.** "영어 잘하는 법"과 "일본어 잘하는 법"은 학습자가 느끼는 지점이 비슷하다. 영어 교육에서 잘된 영상 포맷을 한국어 교육으로 가져와도 통한다.
- 실제 참조 방식은 **썸네일과 제목 수집**이다. 한국에서 잘나가는 영어 교육 채널의 타이틀·썸네일을 보고 자기 콘텐츠로 변형한다. 도입부 구성도 참조한다.
- 범위는 언어 교육을 넘어선다. **"일본에서 인기 있었던 한국 관련 영상"** 전반이 소재가 된다.
  - 예: 한국 드라마(일본에서 유행한 참교육 드라마 등), K-POP 스타, 배우, 한국 여행
  - 이유: 일본인 한국어 학습자는 이런 주제를 좋아하므로 콘텐츠 소재로 전환 가능하다.
- 개발자 코멘트: 카테고리별 인기 순위 형태로 정리하면 재미있을 것 같다.

## 5. 원하는 화면

- **대시보드**에서 기간을 **1주 / 1개월 / 3개월**로 전환하며 뜨는 영상을 본다.
- 그와 별개로 **꾸준히 잘 나가는 영상(에버그린)** 목록도 함께 본다.
- 카테고리별로 "언어 교육에서 이런 소재가 잘 나갔다"를 표시한다.
- 자사 채널 기준으로 어떤 콘텐츠가 성과가 좋았는지도 본다.
- 영상이 마음에 들면 클릭해서 목록에 담을 수 있으면 좋겠다.
- (요청) 등록한 채널의 **일주일 전 대비 구독자 증감**을 보고 싶다 → 개발자 반응: **"어렵다"** (미해결 항목)
- 참조할 UI 목업이 이미 있고, 운영자는 그 인터페이스가 마음에 든다고 했다.

## 6. 데이터 수집 — 개발자의 판단

> "데이터 수집이 좀 어려우실 거예요."

- YouTube Data API를 가져다 쓰는 것이 출발점. 채널 정보 등 기본 정보는 가져올 수 있다.
- 파이썬 계열 라이브러리로도 상당 부분 수집 가능하다. **자료 수집 자체는 어느 정도까지 가능**하다는 결론.
- 다만 **"일주일 동안 조회수가 얼마나 올랐는지"** 같은 시계열 증분은 API로 바로 얻기 어렵다. → 직접 스냅샷을 쌓아야 한다는 뜻.
- 개발자는 별개로 YouTube 데이터를 수집해 NotebookLM 등과 연동, 키워드/주제에 맞는 소스를 모아 지식으로 활용하는 작업을 하고 있다고 밝혔다.

## 7. 프로젝트의 진짜 핵심 — 스코어링 기준

미팅에서 양쪽이 가장 길게 합의한 지점이다.

**운영자**
> "기준 세우는 게 제일 어려웠다. 주관적인 기준 말고 **실제 시장에서 쓰는 기준**이었으면 좋겠다. VidIQ 같이 이걸 이미 서비스로 운영하는 회사들이 있지 않나."
> "사실 제가 생각하기에는 **저게(점수 매기는 방식이) 핵심**이라고 생각한다."

**개발자**
> "그런 회사들은 월 SaaS로 50만 원씩 받는 서비스다. 자기들 데이터로 기준을 세워서 프로그램에 녹여낸 것이다."
> "우리는 대기업 유튜브만큼의 데이터는 없으니, **그 부분을 철저히 조사해서 기준을 잘 세워야 한다.** 데이터를 긁어오는 건 사실 크게 어려운 부분이 아니다. **그걸 어떻게 정제하느냐가 중요하다.**"
> "정제된 데이터를 방금 보여준 UI 대시보드에 얹는 것을 **1차 목표(MVP)** 로 잡고, 거기서부터 확장해 나가자."

**액션**: 다른 사이트들이 점수를 어떻게 매기는지 조사해서 공유하기로 함.

## 8. 기술 제약

| 항목 | 내용 |
| --- | --- |
| 언어 | Ruby |
| 프레임워크 | **Ruby on Rails** (풀스택). 파이썬 아님 |
| DB | **SQLite**. 별도 DB 서버 없이 연결해서 단독 사용 |
| CSS | **Tailwind CSS** — 운영자가 직접 코드 보면서 수정하기 편해서 |

운영자도 코딩을 하고 있고, 넘겨받은 뒤 직접 손볼 것을 전제로 스택을 고른 것이다.
개발자는 **Rails를 얼마나 조사해야 할지 확인이 필요**하다고 했고, 그 부분만 해결되면 진행에 문제없다고 답했다.

## 9. 운영자가 이미 겪은 실패

혼자 만들어보다 막힌 지점들이다. 이번 구현에서 그대로 해결 과제가 된다.

- **로컬에서만 돌려봤는데 잘 안 됐다.** 데이터가 쌓여야 하는데 로컬이다 보니 **컴퓨터가 꺼져 있으면 수집이 끊긴다.** → 상시 실행되는 수집 스케줄러 필요.
- 리서치 도중 **서버에서 막히는(차단되는) 문제**가 있었다. → 레이트리밋/차단 대응 필요.
- **상세하게 계획을 세워본 적이 없다.** MCP로 데이터만 때려박고 영상 만들 때마다 즉흥적으로 확인하는 식이었다. 이번엔 체계화하고 싶다.

## 10. 진행 조건과 다음 액션

- **견적**: 개발자 표현으로 "비싼 프로젝트". 대신 개발자 본인도 유튜브 운영에 관심이 있어 서로 윈윈할 수 있는 영역이라고 봤다.
- **일정**: 다른 프로젝트와 병행하여 **3주 내** 목표. 진행 상황에 따라 **주 1회 미팅**.
- **운영자 → 개발자 (이메일 전달)**
  - [ ] 상세 스펙 문서
  - [ ] UI 목업
  - [ ] 자사 채널 통계 페이지 / 홈페이지 (컨텍스트 참고용) — 개발자가 분석하기로 함
- **개발자**
  - [ ] Ruby on Rails 조사
  - [ ] 타 서비스의 스코어링 방식 조사
- 상세 스펙을 미리 처리해두는 것은 **발주 처리 목적**도 겸한다.

## 11. 미결 / 확인 필요

- 채널 **구독자 증감 추적** — 개발자가 "어렵다"고 답한 뒤 결론 없이 넘어감.
- **스코어링 공식** 자체가 미정. 이 프로젝트의 성패가 여기 걸려 있다.
- 일본 지역 인기 데이터(한국 관련 영상)를 어떤 경로로 수집할지 미정.
- 영상 후반부는 인식 품질이 특히 낮아 세부 합의 내용 일부가 복원되지 않았다. (불명확)
