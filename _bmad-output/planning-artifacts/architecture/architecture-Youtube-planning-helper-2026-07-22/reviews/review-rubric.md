## 종합 판정

**Concern (조건부 합격).** 스파인의 코어 — 레이어 경계·서비스 단일 소재지·스냅샷 단일 원천·튜닝 설정 격리·쇼츠/롱폼 분리·임베딩 저장·잡 분리 — 은 이 프로젝트의 실제 발산점을 정밀하게 고정했고 16개 AD 규칙은 대부분 grep/스키마/리뷰로 강제 가능하다. FR 커버리지도 26/26 완전하고 매핑이 타당하다. **단, 운영/환경 봉투(operational envelope)에서 세 개 차원이 통째로 침묵한다 — SQLite 백업/복원, API 키·시크릿 관리, 초기 백필 실행.** 특히 백업/복원은 스냅샷이 소급 재구성 불가(제약5)라는 이유로 load-bearing이며, 이 침묵은 체크리스트 7의 명시적 파울에 해당한다.

## 항목별 상세

### 1. 발산점 고정 — Pass

에픽/스토리가 서로 다른 세션에서 만들어질 때 어긋날 지점을 스파인이 선제적으로 못박았다.

- **계산의 유일 소재지** — AD-2(스코어링)·AD-10(임베딩)이 "공식을 뷰·잡·모델에 복제 금지"를 규칙화. 튜닝 시 다곳 수정 발산을 차단.
- **외부 호출 경계** — AD-1이 YouTube 호출을 `services/youtube` 단일 통과로 고정. 쿼터 회계·백오프·nil 방어가 흩어지는 발산을 차단.
- **파생값 물질화** — AD-3이 "웹 요청 경로는 재계산 금지, 배치가 물질화한 값만 읽기"로 P95 발산을 차단.
- **시계열 단일 원천** — AD-5가 스냅샷 테이블을 VPD·에버그린·스파크라인의 유일 원천으로 고정하고 `(video_id, date)` 유니크를 강제.
- **콜드스타트 판정** — AD-7이 "전역 배너 하나로 뭉개지 말고 위젯별 준비도"로 못박아, 스토리마다 콜드스타트를 다르게 처리하는 발산을 차단.

**경미한 미고정 — 스냅샷 `date` 타임존.** Consistency Conventions는 "시각은 UTC `datetime`"만 정하고 스냅샷 키 `date`를 **어느 타임존 기준으로 버킷팅하는지** 침묵한다. 일일 잡이 UTC 자정 기준으로 `date`를 계산하는 스토리와 KST/JST 기준으로 계산하는 스토리가 공존하면 `(video_id, date)` 유니크가 의도와 다르게 동작하거나 하루 경계에서 중복/누락이 생길 수 있다. AD-5의 불변식을 완결하려면 date 파생 타임존을 한 줄 고정 권장.

### 2. Rule 강제 가능성 — Pass

각 AD의 Rule을 강제 수단으로 점검했다.

- AD-1·2·4·15 — grep 가능한 금지(직접 호출·상수 하드코딩·raw Tailwind 색). 강함.
- AD-5·6·8·10 — 스키마 제약·컬럼 존재로 강제. 강함.
- AD-11·12·13·14 — 설정 파일/제너레이터 산출물로 강제. 강함.
- AD-16(정직성 상태) — "위젯 숨기지 말고 자리 유지"는 성질상 UI 리뷰 의존이라 상대적으로 무르다. 다만 DESIGN.md §4.7 스타일과 AD-7/8/9의 구체 기전을 그 UI 표면으로 지목해 "막연한 포부"는 넘어섰다. Pass 유지.

### 3. Deferred의 안전성 — Pass

Deferred 7항목 모두 **값을 연기하기 전에 seam을 먼저 고정**한다 — 이게 발산 방지의 핵심이다.

- 튜닝 초기값 → AD-4가 `config/scoring.yml` 자리 고정.
- 상단 퍼널 5번째 요소 → AD-21 정규화 파이프에 "요소 추가"만, "임의 정의 금지" 명시. 지금 정의가 없으니 발산 없음.
- VPD·검증 에버그린·소형 구독자 증감 → AD-5 스냅샷 모델이 "새 테이블 없이 붙는다"로 자리 확보.
- sqlite-vec → AD-10이 임베딩 접근을 `services/embedding`로 캡슐화해 드롭인 전환 가능.
- 프로세스 모델(Puma 인프로세스 vs `bin/jobs` 별도) → either/or로 열렸으나 Solid Queue가 잡 작성 코드를 추상화해 스토리 발산 없음.

load-bearing 항목이 seam 없이 연기된 사례는 없음.

### 4. 기술 최신성 — Pass (상세 위임)

- **Rails 8.x / Solid Queue / Solid Cache** — Solid Queue·Cache는 실제 Rails 8 기본 어댑터. 정합.
- **YouTube Data API v3** — 현행 유일 버전.
- **SQLite 3.x WAL 멀티DB** — Rails 8이 공식 지원.
- **Tailwind CSS 3.x** — 4.x가 이미 출시됨. 다만 스파인이 DESIGN.md §10 토큰을 `theme.extend`로 이관(4.x는 CSS-first 설정)하고 `tailwindcss-rails`를 쓰는 맥락상 3.x 핀은 의도적 선택으로 읽힌다. **명백한 노후는 아님** — 3.x vs 4.x 채택 판단은 tech-currency 리뷰어에 위임.
- **gemini-embedding-001** — 실재 모델. "현행" 표기. GA 상태·정확한 모델 ID·요금은 tech-currency 리뷰어에 위임.

명백히 stale한 명명은 없음.

### 5. 고도 정합(과대/과소명세) — Pass

그린필드 스파인으로서 과대명세를 잘 피했다. ERD는 "이름·관계만", 소스트리는 "비자명한 곳만", 그리고 "속성 중 불변인 것은 다이어그램이 아니라 AD가 정의한다"고 명시해 코드가 소유할 디테일을 스파인이 미러하지 않는다. 클래스명(`Scoring::CalculateBaseline` 등)은 예시·컨벤션 수준이라 적정. AD-11의 체인 순서 고정은 코드 디테일이 아니라 "순서=의존"의 불변식이라 정당. **과소명세는 오직 운영 봉투(항목7)에 국한**되며 코어 아키텍처 고도는 정확하다.

### 6. FR 커버리지 — Pass

Capability→Architecture Map에 FR-1~FR-26 26행 전부 존재하고 frontmatter `binds`도 26개 완전. 각 매핑을 타당성 점검한 결과 모두 합리적(스코어링→services/scoring, 임베딩→services/embedding+OwnVideoMatch/TopicCluster, 시계열→스냅샷+AD-7/16 등).

**경미 — FR-15 매핑이 얇다.** FR-15(경쟁 채널 자동 추천 + URL 수동 등록/제외 + 시드 로드)를 `channels 컨트롤러 + seed / AD-1` 단독으로 매핑했다. AD-1은 API 호출 경계일 뿐, 채널 등록/제외 쓰기·채널 URL 파싱/검증·시드 목록 로드를 규율하는 AD가 없다. 발산 위험은 낮지만(2인 도구), URL 파싱 규칙이나 제외=soft delete vs hard delete 같은 결정이 스토리 사이에서 갈릴 여지는 있다. 필요 시 컨벤션 한 줄 보강 권장.

### 7. 운영/환경 봉투 — Fail (핵심 파울)

체크리스트가 명시적으로 열거한 하위 차원 대비 점검. 스파인 본문 grep 결과 `backup`/`restore`/`백업`/`복원`/`secret`/`credential`/`자격`/`key`/`백필`/`backfill` **모두 0회**.

- **배포 & 환경** — Deferred "배포·환경 상세"에서 소형 VPS 상시 실행, Puma+Solid Queue 인프로세스 or `bin/jobs` 별도로 **접촉은 했다**. 다만 dev/staging/prod 환경 구분은 무언급. 2인 도구 맥락상 얇아도 허용 가능. → **접촉함(연기).**
- **인프라/프로바이더** — 소형 VPS로 접촉. → **접촉함(연기).**
- **운영(관측성)** — AD-13 `job_runs`+백오프+"운영자가 DB로 확인"으로 최소선 결정. 실패 알림 채널은 없으나 주1회 도구라 허용. → **결정됨(최소).**
- **SQLite 파일 백업/복원** — **통째로 침묵. [FINDING·High]** 이 시스템의 유일무이한 가치는 소급 재구성 불가한 일별 스냅샷이다(제약5 "시점 정합 소급 불가", FR-3). YouTube는 과거 시점 조회수를 돌려주지 않으므로 `app.sqlite3` 디스크가 날아가면 축적된 시계열 전체가 **영구 소실·재취득 불가**다. WAL·`VACUUM`·멀티DB는 다뤘지만 백업/복원 정책(스냅샷 빈도·오프박스 저장·복원 절차)은 어떤 AD·Deferred에도 없다. 데이터 비가역성 때문에 이 차원은 load-bearing이며, 침묵은 체크리스트 7의 정의상 finding.
- **임베딩 API 키·시크릿 관리** — **침묵. [FINDING·Medium]** PRD는 "YouTube와 같은 Google 계정·다른 키"로 키 2종(YouTube Data API·Gemini) 존재를 명시하나, 스파인은 이 키들을 어디서 관리하는지(Rails credentials vs ENV vs `config/`) 컨벤션을 안 준다. 한 스토리가 `ENV['GEMINI_KEY']`를, 다른 스토리가 `Rails.application.credentials`를 읽으면 발산한다. AD-4가 튜닝값 설정 소재지를 고정한 것과 대칭으로, 시크릿 소재지도 한 줄 고정이 마땅.
- **초기 백필 실행** — **스파인에 부재. [FINDING·Medium]** PRD §4.1·§9.2가 1회성 백필을 명시한다(전체 영상 열거 ≈400 units, 자사 500+경쟁 ~1.5만 임베딩 ≈$0.3~0.5). 이는 AD-11의 정상상태 일일 체인(`playlistItems` 채널당 하루 1페이지=증분 열거)과 **다른 코드 경로**(전체 열거+전량 임베딩)다. 스파인엔 BackfillJob도, "첫 실행은 어떻게 다른가" seam도 없다. 백필을 구현하는 스토리와 일일 체인을 구현하는 스토리가 열거 범위·임베딩 트리거를 서로 다르게 가정해 발산할 수 있다. Deferred 또는 AD로 최소한 "1회성 백필 잡이 존재하고 정상 일일 체인과 분리된다" 정도의 자리 고정 권장.

**요지:** 명시 열거된 6개 하위 차원 중 백업/복원·시크릿·백필 3개가 침묵 또는 스파인 미반영이며, 그중 백업/복원은 데이터 비가역성으로 load-bearing이다. → **Fail.**

## 우선순위 발견 (severity 순)

1. **[High] SQLite 백업/복원 차원 침묵** — 스냅샷은 소급 재구성 불가(제약5)라 `app.sqlite3` 소실 = 시계열 영구 소실. 어떤 AD·Deferred도 백업/복원을 다루지 않음. (체크리스트 7)
2. **[Medium] API 키·시크릿 관리 컨벤션 부재** — YouTube·Gemini 키 2종의 소재지(credentials vs ENV) 미고정으로 스토리 발산 가능. (체크리스트 7)
3. **[Medium] 초기 백필 실행이 스파인 미반영** — PRD가 정의한 1회성 전체 열거+전량 임베딩 백필이 AD-11 정상 체인과 분리된 seam 없이 부재, 백필/정상 스토리 발산 위험. (체크리스트 7)
4. **[Low] FR-15 매핑이 얇음** — 채널 등록/제외·URL 파싱·시드 로드를 규율하는 AD 없이 AD-1 단독. (체크리스트 6)
5. **[Low] 스냅샷 `date` 타임존 미고정** — datetime=UTC만 정하고 스냅샷 키 `date`의 버킷팅 타임존 미정의, 하루 경계 중복/누락 여지. (체크리스트 1)

## 권고

코어 아키텍처는 견고하니 재작성이 아니라 **운영 봉투 보강**이면 충분하다. 최소 처방:

- Deferred에 **백업/복원 정책** 한 항목 추가(예: 일일 잡 종료 후 `app.sqlite3` 스냅샷 오프박스 복사, 복원 절차 자리 고정). 비가역 데이터라 "운영 인수 시점에 정한다"로 미루기엔 리스크가 크다.
- Consistency Conventions 또는 새 AD로 **시크릿 소재지**를 한 줄 고정(Rails credentials 권장).
